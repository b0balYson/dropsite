# MCP tools

Both MCP servers offer the same tools with the same names, descriptions, schemas and hints: the remote endpoint `/mcp` and the local `dropsite mcp` (see [ai-clients.md](ai-clients.md)). The only difference is the publication tool: `deploy_files` on the remote server, `deploy_folder` on the local one. `cmd/dropsite/mcp_parity_test.go` compares both tool lists.

The inventory at the end of this page is generated from the tool definitions in `internal/mcp`; `go test ./internal/mcp` fails when it is out of date. Regenerate it with:

```sh
go test ./internal/mcp -run TestToolsDoc -update
```

## Conventions

The users are mostly non-technical; the model picks a tool by its name and description. New tools follow these rules (`internal/mcp/catalog_test.go` checks the mechanical ones):

- **Names** are `verb_noun`. `list_*` lists, `get_*` reads one thing, `create_*` makes a new thing, `set_*` replaces a setting (idempotent), `save_*` creates or changes, `update_*` changes part of a thing, `add_*`/`remove_*` attach and detach, `delete_*` destroys. Specific verbs are used where they say more: `publish_draft`, `discard_draft`, `rollback`, `clone_site`, `schedule_publish`, `link_sheet`, `sync_sheet`, `moderate_documents`, `rotate_channel_secret`, `revoke_connection`.
- **Descriptions** are plain English. The first sentence says when to call the tool, with a user phrase where it helps; then what to tell the user; then which sibling tool fits better for nearby requests (files vs collection data, draft vs schedule vs direct publication, proxy vs external backend, starter templates only on request).
- **Parameters**: the site is always `site` (ID or slug, as `list_sites` returns it); a workspace is `workspace` (the `workspace_id` of `list_workspaces`); versions are `deploy_id`, and the version a change is based on is `base_deploy_id`. Every parameter has a description.
- **Closed choices** that the server compares exactly are enumerated in the schema (`get_guide.topic`, `begin_upload.mode`, `device`). Choices the server normalises (any case, surrounding spaces) and answers with a fix-it error are listed in the description only, so that a slightly different spelling still works: `add_channel.kind`, `save_collection.mode`, `list_documents.status`, `moderate_documents.action`, `set_proxy_endpoint.auth`, `lang`.
- **Destructive tools** are marked `destructiveHint`, say in the description that the user must confirm first, and take `confirm`: the name, slug, ID, e-mail or domain repeated after the user's explicit yes. A wrong `confirm` changes nothing and the error says how to ask.
- **Results** carry links ready to show (`url`, `preview_url`, `secret_url`, `cabinet_url`) and, where helpful, a `summary` or `next_step` in plain words. Errors say what to fix.
- **Secrets** never appear in results: no API keys of proxy endpoints, no Google service account key, no tokens. The only exception is the webhook signing secret, returned once by `add_channel` (kind `webhook`) and by `rotate_channel_secret`.
- `get_site` alone returns `attached` (what is set up on the site); the other site tools return the shorter site object.

## Known inconsistencies kept for compatibility

Renaming a tool or a parameter breaks chats that are already connected, so these stay as they are:

- The collection is `name` in `save_collection` and `delete_collection`, but `collection` in the document and Google Sheets tools. In `list_collection_templates`, `name` is the template and `collection` the collection name used in the snippet.
- `set_slug` does the same as `update_site` with only `slug`. Its description says so; the guide uses `update_site`.
- `save_documents` (with `replace`), `delete_documents` and `moderate_documents` (with `reject`) are destructive but have no `confirm` parameter; their descriptions require the user's explicit yes.
- `list_deploys` and `deploy_id` say "deploy" where descriptions and the guide say "version".
- `openWorldHint` is false for `update_site_files` and `upload_files` (their `fetch` downloads public files) and for the Google Sheets tools. Only `inspect_reference`, whose purpose is to read another site, is marked open-world, so that chat clients do not ask for extra approval on every file change.
